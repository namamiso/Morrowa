## 調査結果

### Bug3: グリッド色が更新されない — 原因確定 (調査エージェント報告 2026-07-24)

- **根本原因**: `ui/HabitScreen.kt:127-138` — 画面上部の年間草カレンダーに `completedDays = emptySet()` がハードコードされたまま(プレースホルダ)。`onDayToggle = {}` も no-op。DB に何が入っていても色は絶対に変わらない。再起動しても変化しない症状と完全一致。
- 導入経緯: コミット `c4c6288491`(workspace 埋め込み)からプレースホルダのまま。Phase 3-E で配線されたのは習慣ごとの展開カレンダーのみ。
- 検証済みのシロ: 日付キー(ISO yyyy-MM-dd, JST 固定)は書き込み/描画で一致。DAO は Flow 購読で invalidation も正常。書き込み経路(`checkHabit`→`toggleCompletion`)も正常。
- **修正案(最小)**: `HabitDao` に `SELECT DISTINCT habitDay FROM habit_completions` の Flow クエリを追加し、Repository→ViewModel(StateFlow)→HabitScreen と配線。スキーマ変更不要。
- 仕様判断: 上部カレンダーの緑は「1件でも完了があれば」とする(全習慣達成判定は将来課題)。
- 副次的発見:
  1. `HabitViewModel.refreshHabitDay()`(HabitViewModel.kt:58)が**どこからも呼ばれていない** → Bug2 の有力原因。なお日付境界は 4:00(HabitDay.kt:11)であり5時ではない。
  2. `HabitScreen.kt:219` — 再コンポーズごとに `getCompletionsFlow()` を再生成し DB オブザーバを張り直している。`remember(habit.id)` でラップすべき。
  3. `GrassCalendar.kt:45` が常に現在年を使い、YearSelector が飾りになっている(今回のスコープ外として記録のみ)。
  4. `MorrowaWorkspacePageView.kt:25-26` — `setContent` ラムダ内で ViewModel を直接生成(リーク性)。`remember`/フィールド化すべき。

### Bug2: 日付切替が再起動まで反映されない — 原因確定 (調査エージェント報告 2026-07-24)

- 前提訂正: 日付境界は仕様書どおり **4:00**(HabitDay.kt:11)。「朝5時」はユーザー体感で、コード上の境界自体は仕様どおり。
- **根本原因**: `HabitViewModel.kt:30` — `_habitDay = MutableStateFlow(HabitDay.today())` が ViewModel 構築時に一度だけ評価され固着。更新用 `refreshHabitDay()`(同:58)の呼び出し元が**ゼロ**。日付変化の検知機構(DATE_CHANGED receiver / 4:00 アラーム / ポーリング / lifecycle フック)がコードベースに一切存在しない。
- ViewModel は `MorrowaWorkspacePageView.kt:25` で直接 new され、Workspace 常駐のため再起動までインスタンスが生き続ける(「再起動で直る」の説明)。
- **隠れた実害**: `checkHabit`(HabitViewModel.kt:62-66)が固着した古い `habitDay` で書き込むため、4:00 以降のチェックが**昨日のレコードとして記録され、トグルで昨日の記録を消し得る** = データ整合性バグ。
- 下流(completions の flatMapLatest、HabitScreen の collectAsState、GrassCalendar の isFuture)はすべて `habitDay` StateFlow に正しく従属しており、emit さえすれば全部直る。
- **推奨修正**: 案A(view attach / ON_RESUME 時に `refreshHabitDay()`)+ 案C(次の 4:00 までコルーチン `delay` するループ)の併用。加えて `checkHabit` は書き込み時点で `HabitDay.today()` を再評価する。AlarmManager 案は重いため不採用。
- 横展開メモ: ToDoScreen の期限切れ判定にも「再コンポーズが起きなければ古いまま」の同種潜在バグあり(記録のみ)。

### Bug1: グリッド横スワイプが負ける — 原因確定 (調査エージェント報告 2026-07-24)

- **原因A(本命)**: 親 `Workspace.onInterceptTouchEvent` は常に子(Compose)より先に走る。0°〜30°のほぼ水平なドラッグでは Workspace は slop 減衰なし(`Workspace.java:1490-1491`)で、GrassCalendar 側(`GrassCalendar.kt:73,86`)と**閾値が完全同値**。slop を跨いだ瞬間のイベントで Workspace が先に intercept し、Compose には ACTION_CANCEL しか来ない → 真横スワイプは 100% 負ける。30°〜45°の斜めだけ勝てる(Workspace 側 slop が最大3.83倍に減衰されるため)。1d2f24128f の「グリッド側の slop の方が小さい」という前提が誤りだった。
- **原因B(間欠)**: ページ慣性スクロール中のタッチは DOWN 時点で `mIsBeingDragged = true`(`PagedView.java:1142-1156`)となり、DOWN 自体が Compose に届かない。
- **原因C(設計弱点)**: `requestDisallowIntercept` の解除経路が無く、中間 ViewGroup にフラグが残留し伝播が止まり得る。
- **修正案比較**:
  - 案A(DOWN 即 disallow): DragLayer の TouchController(All Apps 上スワイプ等)が壊れるため**非推奨**(`AbstractStateChangeTouchController.java:92-122` が DOWN でしか初期化されない)。
  - **案B(推奨)**: Workspace 側にグリッド領域除外フラグ。既存の `mIsEventOverFirstPagePinnedItem`(QSB 上でページングを殺す仕組み、`Workspace.java:1412-1433, 1462`)と同一パターン。レースが原理的に消え、縦ジェスチャ無傷、原因A/B/C 全対応。
  - 案C(グリッド上だけ slop 減衰): 確率的挙動が残る。案D(NestedScroll): 工数過大。
- 案B採用時は GrassCalendar.kt:70-92 の現行 pointerInput は不要になる。

### Bug4: エクスポートで習慣/ToDo が固まる — 原因確定 (調査エージェント報告 2026-07-24)

- **根本原因**: `ui/BackupScreen.kt:60-83` の `rememberLauncherForActivityResult` は `ActivityResultRegistryOwner` を composition 中に必須とするが、ホストの Launcher は `BaseActivity extends Activity`(ComponentActivity ではない、`BaseActivity.java:77-78`)で Registry を提供していない → `IllegalStateException` が composition 中に throw。
- **凍結のメカニズム**: Compose の Recomposer は window ごとに1つ。composition 中の例外で Recomposer が `ShutDown` になり、Launcher window 内の**全 ComposeView**(習慣・ToDo・ダイアログ)が再コンポーズ不能に。ランチャー本体は View 実装なので無傷。プロセス再起動まで復活しない。症状3点(両方固まる/ランチャーは無事/再起動で直る)と完全一致。
- 発火タイミングはエクスポートボタンではなく、バックアップアイコン押下で `BackupScreen` が composition に入った瞬間。
- スレッド/Mutex/デッドロック系の仮説はすべてシロ(runBlocking 無し、Mutex 無し、スコープ共有無し)。
- **推奨修正(案B)**: `MorrowaBackupActivity : ComponentActivity` を新設して `BackupScreen` をそちらに出す。Lawnchair の `PreferenceActivity` と同じ構図。BackupScreen はほぼ無改造で流用可。原則: **Launcher window の composition 内で `rememberLauncherForActivityResult` を呼ばない**。
- 副次バグ(併修推奨): (b) `MorrowaBackup.serialize()` がメインスレッド実行 → IO へ、(c) `AlarmRepository(context)` を IO スレッドで生成すると `MainThreadInitializedObject` がメインスレッド待ちブロック、(a) `isWorking` ラッチ(専用 Activity 化でほぼ解消)、(f) インポートの長時間トランザクション(記録のみ)。

## 決定事項 (2026-07-24, Plan エージェント合議で確定)

1. **フェーズ順序**: 0(土台) → 1(Bug3) → 2(Bug2) → 3(Bug4) → 4(Bug1) → 5(レビュー)。リスク昇順、Launcher3 コアに触る Bug1 を最後に。Bug4 を Bug1 より先にやることで、Bug1 のヒット矩形無効化条件が `!showTrash` だけで済む。
2. **Phase 0 の位置づけ格上げ**: `DisposeOnDetachedFromWindow` のため detach→reattach ごとに ViewModel が再生成されリークする。VM のフィールド化は Bug2 だけでなく全修正の土台。死にコード(`MorrowaOverlayView.kt`, `MorrowaTouchController.kt`)は Phase 0 で削除する(`MorrowaPageController` は現役なので残す)。
3. **Bug2 タイマーの置き場**: ViewModel 内ループと repeatOnAttached は**却下**(`delay` は uptime ベースで doze 中に止まり、ドリフトして同種バグが再発する)。**HabitScreen 内 `repeatOnLifecycle(RESUMED)` の while ループを採用**。BaseActivity は LifecycleHelper で decorView に LifecycleOwner を供給済みで、Launcher window 内 Compose でも正しく動くことを裏取り済み。resume 初回イテレーションで即 `refreshHabitDay()` されるため attach/resume 再計算も兼ねる。境界残時間計算 `millisUntilNextBoundary()` は HabitDay に置く。
4. **checkHabit は書き込み時に `HabitDay.today()` を再評価**し、同時に `_habitDay.value` も更新して UI と書き込み先を一致させる(昨日のレコードを消し得る整合性バグの直接の栓)。
5. **Bug3 の DAO クエリはゴミ箱除外の JOIN**: `SELECT DISTINCT c.habitDay FROM habit_completions c JOIN habits h ON h.id = c.habitId WHERE h.deletedAt IS NULL`。上部カレンダーの緑は「1件でも完了があれば」(全習慣達成判定は将来課題)。`onDayToggle` は nullable 化し年間側は null(clickable 除去)。
6. **Bug1 は (a)+(b) ハイブリッド**: GrassCalendar が `onGloballyPositioned`(boundsInRoot ≒ MorrowaWorkspacePageView ローカル座標)で矩形をレジストリ登録、Workspace は `isEventOverQsb` パターンの写経で DOWN 時に `isPointOverHorizontalScroller()` へ問い合わせ。落とし穴対応: ゴミ箱オーバーレイ表示中は矩形登録を止める(`registerHitRect = !showTrash`)。慣性スクロール中 DOWN(原因B)は `updateIsBeingDraggedOnTouchDown` で PagedView 既存分岐の写しでページ確定させて対応。旧 pointerInput(GrassCalendar.kt:70-92)は削除(原因Cも自動消滅)。
7. **Bug4**: `MorrowaBackupActivity : ComponentActivity` 新設(exported=false, Theme.Lawnchair)。専用 Activity では不透明背景・`onBack = finish()`。`serialize()` は IO へ、Repository 生成は `withContext(IO)` の**外**(メイン)で(MainThreadInitializedObject のバックグラウンドブロック回避)。ファイル書き込みは NonCancellable で保護。
8. **受け入れ条件は3層**: (i) フェーズ固有の grep アサーション、(ii) 実装に関与していないサブエージェントによる diff レビュー(import/型整合 + 因果チェーンのトレース)、(iii) Phase 5 でユーザー向け実機テスト手順書(Bug2 は「時計を 3:59→4:01 に変更→ホーム復帰」で RESUMED ループ再起動を踏む手順)。
9. この環境はビルド不可のため、最終ビルド・実機確認はユーザーの Mac で実施。

## 実機検証手順 (ユーザーの Mac でビルド後)

### Bug1: グリッドスワイプ
1. 習慣ページで草カレンダー(上部年間・習慣別展開の両方)を**真横に**ゆっくり/速くスワイプ → グリッドがスクロールし、ページが動かないこと
2. **Home から習慣ページへ fling した直後**(セトリング中)にグリッドをスワイプ → グリッドが勝つこと
3. **ゴミ箱を開いて閉じた後**にグリッドをスワイプ → グリッドが勝つこと(R-2 の確認)
4. 回帰: グリッド外の横スワイプでページ移動、All Apps 上スワイプ、QSB、ウィジェットの縦スクロールが正常なこと

### Bug2: 日付切替
1. 設定アプリで時刻を 3:59 に変更 → ホームに戻る → 4:01 に変更 → ホームに戻る → 習慣ページの日付が翌日になっていること(再起動不要)
2. 習慣ページを表示したまま 3:59→4:00 を跨ぐ(画面点灯のまま)→ 表示が切り替わること
3. 4:00 直後にチェック → 新しい日のマスに記録されること(昨日の記録が消えないこと)

### Bug3: グリッド色
1. 習慣にチェックを付ける → 上部年間カレンダーの今日のマスが即座に緑になること
2. チェックを外す → 即座に色が戻ること
3. ランチャー再起動後も過去の完了日が着色されていること
4. ゴミ箱に入れた習慣の完了履歴が上部カレンダーに含まれないこと

### Bug4: エクスポート
1. バックアップアイコン → 専用画面が開くこと(固まらないこと)
2. エクスポート実行 → JSON が保存され、戻った後も習慣/ToDo の操作が正常なこと
3. インポート往復(エクスポート→インポート)でデータが一致すること
4. エクスポート中に戻る操作をしてもファイルが壊れていないこと
